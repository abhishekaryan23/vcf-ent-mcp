# Independent review: VCF Enterprise MCP (unofficial) — guided setup, architecture, VCF 9.x fit

Reviewer: independent (senior VCF 9.x architect / MCP / enterprise security). No repository files were modified; no plans were approved. All state lived in `<tmp>/review/` (HOME and every `VCF_MCP_*` path pointed there). Target: the running Northwind simulation (12 appliances on 127.0.0.1:9601–9641, lab CA `northwind_mock/runtime/ca.pem`).

## Verdict

The pieces that exist are better than most "MCP for X" projects: per-component VCF 9.x session auth is correct, the loopback credential page is genuinely well engineered (single-use ticket, CSRF, Host check, verification code, detached process surviving LM Studio restarts), the safety profile can only be loosened from a local TTY, and once correctly configured the multi-vCenter inventory and `vcf_diagnose` found the Northwind DFW root cause in one call. But the owner's top priority, "very easy guided setup from any harness", is **not met today**: following the README literally (`token mint` → `claude mcp add … vcf-enterprise-mcp` → "set up VCF MCP") the server crashes before the first MCP message, because the guided setup can only run inside a server that already has a complete config, which the guided setup is supposed to create. Even after a user discovers `vcf-mcp setup`, connecting to a lab with a private CA, loopback/alias URLs or non-RFC1918 addressing requires three undocumented hand edits of `config.yaml` (`allow_loopback_targets`, `ca_cert_path`, `allowed_dns_suffixes`/`endpoint_overrides`), each failure wipes the passwords the user just entered, and the resulting half-configured server reports the MCP's own SSRF block as "most likely cause: vCenter … could not reach the appliance" with medium confidence. Multi-NSX inventory, VCF Automation credentials, proxies and public-IP estates are not handled by setup at all. The test suite passes (466 passed, 28 s) but exercises none of these cold-start paths. Fix the Critical/High items below before letting anyone outside the lab try it.

## Top 5 changes to make setup effortless

1. **Boot into setup mode instead of crashing.** No config or no endpoints → start with `vcf_setup`/`vcf_access_report`/`vcf_find_tool` only, and hot-reload after `COMPLETE`. Make `vcf-mcp client-config` create the state directory and minimal config. This alone turns the README's three steps from impossible into true (F1, F5, F16).
2. **Verify what the estate actually is, not just what was typed.** After the SDDC login, discover vCenters and NSX Managers, probe them with the same account, extend the allowlist from what resolved, and ask for alias/CA/CIDR only when a probe fails. Never blame an appliance for an MCP policy block in `vcf_diagnose` (F2, F6, F14).
3. **Keep the passwords and name the fix.** On verify failure, delete a secret only on 401/403; otherwise return `cause` + `fix` with the exact YAML (`ca_cert_path`, `allowed_dns_suffixes`, `allow_loopback_targets`, proxy) and a `retry` that does not re-ask for credentials (F3, F8).
4. **Close the approval loop inside the chat.** Every dry-run must carry `how_to_approve` (exact CLI with `--db`, what to paste back) and a `vcf_get_plan` tool must return the initiator's `approval_id`/`nonce` once a human has approved, so Claude Desktop/LM Studio/Cursor users never need a custom JSON-RPC method (F10).
5. **One token story, one launch command, one state directory.** `client-config` should mint nothing but should say: "setup needs MCP_ADMIN; daily use needs a role token"; README/harnesses/guided_setup must show the same `vcf-mcp server --mode stdio` command, the same `~/.vcf-mcp` directory, and real role names. Fix the notification reply and let `initialize` succeed without a token so harness logs show a useful error instead of "process exited" (F9, F15, F17, F20).
